## 1. Цель работы

Подключить браузерное приложение со списком задач к изменяемому учебному HTTP API: расширить общий HTTP-клиент методами `POST`, `PATCH`, `DELETE` и JSON-телом, реализовать операции над задачами и контроллер с состояниями `loading`, `ready`, `empty`, `error`, а также защиту от гонки запросов. Источником данных остаётся сервер: после каждого изменения список запрашивается заново.

## 3. Реализация

### 3.1. HTTP-клиент

`requestJson(path, { method, query, body, signal, timeoutMs })` в `src/api-client.js` поддерживает `GET`, `POST`, `PATCH`, `DELETE`; метод приводится к верхнему регистру, другие методы и `body` у `GET` отклоняются `TypeError` до сетевого запроса. К каждому запросу добавляется `Accept: application/json`, а при наличии тела объект сериализуется через `JSON.stringify` и добавляется `Content-Type: application/json` (без тела этот заголовок не отправляется). Сохранены тайм-аут (`AbortSignal.timeout`) и внешняя отмена (`AbortSignal.any`), виды ошибок `http`, `network`, `invalid-response`, `timeout`, `aborted`. HTTP-ошибка проверяется раньше `Content-Type`, сохраняет `status`, `code`, `details`, `url`. Ответ `204` возвращается как `null` без чтения тела.

### 3.2. Доменный API

В `src/task-api.js` реализованы `getTasks`, `getTaskById`, `getCategories`, `loadInitialData` (параллельно через `Promise.all`), `createTask` (`POST /tasks`), `updateTask` и `setTaskCompleted` (`PATCH /tasks/:id`), `deleteTask` (`DELETE`, ожидается строго `null`) и `resetDemoData` (`POST /debug/reset` без тела). Каждый метод данных принимает последним аргументом `{ signal }`. Схема ответа проверяется в самом модуле: каждая задача и категория по `isTask`/`isCategory`, уникальность `id`, соответствие `meta.total`, форма ответа на сброс; нарушение даёт `ApiError` вида `invalid-response`. Модуль не работает с DOM и не формирует сообщения пользователю. Фильтры проверяются до запроса (`completed`, `priority`, `categoryId`, `q`).

### 3.3. Состояния интерфейса

`createAppController` (`src/app-controller.js`) хранит снимок задач, категории, фильтры, `editingId`, активный `AbortController` и номер загрузки. Загрузка: `loading` → при успехе `ready` (есть задачи) или `empty` (результатов нет, это не ошибка) → при ошибке `error` с понятным сообщением (`messageForError`) и кнопкой повтора. Пока категории не получены, повтор снова вызывает `loadInitialData`, после этого используется `getTasks`. Отменённый запрос ошибкой не показывается.

### 3.4. Изменение данных

Создание, редактирование, смена статуса, удаление и сброс выполняются по общей схеме `mutate`: блокировка кнопок (`setMutationPending(true)`) → запрос изменения → уведомление об успехе → повторный `GET` с текущими фильтрами → разблокировка (в `finally`). Повторный вызов во время выполнения операции игнорируется, поэтому двойной щелчок не создаёт два запроса. Перед созданием и редактированием форма проверяется `validateTaskDraft` (название после `trim`, приоритет, существующая категория); при ошибке запрос не отправляется, ошибки показываются у полей. Идентификатор и начальный `completed` назначает сервер. Локальный массив служит снимком последнего ответа, `localStorage` не используется.

### 3.5. Защита от устаревшего ответа

Перед каждой загрузкой предыдущий запрос отменяется через `AbortController`, а каждой загрузке присваивается порядковый номер. Результат применяется только если номер совпадает с последним. Вторая проверка нужна даже при отмене: источник данных может завершиться, не отреагировав на сигнал немедленно. Отмена из-за смены фильтра не считается ошибкой и пользователю не показывается.

**Разбор единственной ошибки.** В готовом файле `checks/browser.checks.js` проверка создания ждёт карточку так: `await waitFor(() => requireNode(doc, '[data-task-id="35"]'), ...)`. Функция `requireNode` выбрасывает исключение, если элемента ещё нет, а `waitFor` не перехватывает исключения условия, поэтому первый же опрос (сразу после отправки формы, до ответа сервера) завершает проверку ошибкой. Остальные проверки ожидают через логические условия. Это не ошибка реализации приложения: вручную в приложении создание работает (карточка с `id = 35` появляется, форма очищается, всего 13 задач), что подтверждено шагом 2 индивидуального сценария и ручной проверкой ниже. При диагностическом прогоне с временной правкой только `waitFor` (условие обёрнуто в `try/catch`) все проверки прошли:

```text

```

Правка проверок в репозиторий не включена: `checks/browser.checks.js` остался в исходном виде. В первом прогоне оригинала также наблюдалась вторая ошибка (на 13 вместо 12 задач в соседней проверке), её причиной было позднее завершение запроса создания после этой же ошибки (гонка с `reset`); при повторном прогоне она не воспроизвелась.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   Для `fetch` ответ с любым HTTP-статусом — успешно полученный ответ сервера. Promise отклоняется только при сетевой проблеме или отмене, поэтому статус нужно проверять явно через `response.ok`.
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   У `204 No Content` пустое тело, а `response.json()` для пустой строки завершится ошибкой разбора. Клиент возвращает `null` до попытки чтения.
3. **Чем состояние `empty` отличается от `error`?**
   `empty` — запрос успешен, но подходящих задач нет (нормальный результат фильтра). `error` — запрос не удался (сеть, тайм-аут, HTTP-ошибка, неверный формат); для него показывается сообщение и кнопка повтора.
4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Иначе медленный старый ответ может прийти позже нового и перезаписать список. Отмена освобождает ресурсы, а номер загрузки дополнительно защищает от применения устаревшего результата.
5. **Почему после мутации список повторно запрашивается у API?**
   Сервер — источник истины. Повторный `GET` с текущими фильтрами показывает только подтверждённое сервером состояние (например, созданная задача появится только если подходит под фильтр, а выполненная исчезнет из «В работе»).

Браузерное приложение подключено к изменяемому API: создание, редактирование, смена статуса и удаление выполняются через сервер, после каждого изменения список запрашивается заново. Реализованы состояния loading, eady, empty, error и защита от устаревших ответов (отмена предыдущего запроса и проверка номера загрузки). В готовых браузерных проверках одна проверка создания задачи не ожидает ответа сервера из-за исключения в waitFor; приложение работает, что подтверждено вручную и диагностическим прогоном (14 из 14).
