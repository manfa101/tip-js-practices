## Полученный результат

Реализован хук `useTaskData` (`src/hooks/useTaskData.js`), синхронизирующий React-состояние с учебным API: загрузка задач и категорий по текущим фильтрам, обновление, создание, редактирование, смена статуса, удаление и сброс набора. Остальные файлы заготовки (HTTP-клиент, предметный API, компоненты) использованы как предоставлены. Данные хранятся в памяти процесса API: они сохраняются между запросами и обновлением страницы, но после перезапуска сервера возвращается исходный набор из 12 задач.

## Архитектура

- `src/api-client.js` — общий HTTP-клиент (JSON, тайм-аут, отмена, `ApiError`), `src/task-api.js` — операции над задачами и проверка схемы ответов, `src/config.js` — создаёт `api` один раз вне компонента, поэтому ссылка стабильна между рендерами.
- `src/hooks/useTaskData.js` — единственное место работы с эффектами: загрузка, отмена, мутации. Компоненты (`TaskForm`, `TaskFilters`, `TaskList`) только отображают данные и вызывают обратные вызовы; `App` владеет фильтрами и снимком редактируемой записи.
- **Состояние хука:** `snapshot` (последний успешный `{ tasks, categories, meta }`), `status` (`loading`/`ready`/`error`), `error`, `mutationError`, `pending`, `revision` (счётчик обновлений).
- **Эффект загрузки** зависит от `api`, четырёх значений фильтров и `revision`. В зависимостях нет `snapshot`: результат загрузки не должен её запускать. Cleanup отменяет запрос (`AbortController`) и сбрасывает признак `active`.
- **Служебные ref:** `mountedRef` (признак монтирования, восстанавливается в setup эффекта для StrictMode) и `mutationRef` (контроллер активной мутации: блокировка повторного вызова и отмена при размонтировании).
- **Отличия от ПР7:** данные не импортируются в интерфейс, а загружаются с сервера; `id` и `completed` назначает сервер; фильтры передаются API, а не применяются локально; `onSave` возвращает `Promise<boolean>`; статистика относится к последней полученной выборке (`meta.total` — размер выборки после серверных фильтров, а не всех записей).

## Загрузка и изменения

- **Старые ответы подавляются** двумя способами: cleanup эффекта отменяет прежний GET, а признак `active` не даёт устаревшему результату изменить состояние ни в `then`, ни в `catch` (запоздавшая ошибка тоже игнорируется).
- **Повторная мутация блокируется** `mutationRef`: контроллер сохраняется синхронно до первого `await`, поэтому второй синхронный вызов сразу получает `false` (одной переменной `pending` в state для этого недостаточно, обновление состояния происходит асинхронно).
- **Ошибка POST и ошибка последующего GET различаются:** ошибка записи попадает в `mutationError`, ошибка чтения — в `error`/`status: 'error'`. Успешная запись, за которой GET завершился ошибкой, остаётся успешной (`saveTask` вернул `true`), а ошибка показывается как ошибка обновления списка.
- **Черновик при ошибке сохраняется:** форма очищается только при `true`; при `false` введённые значения остаются, ошибка выводится в `role="alert"`, блокировка снимается. Смена фильтра не стирает черновик редактируемой записи, потому что `App` хранит её снимок.
- После успешной мутации увеличивается `revision`, и эффект выполняет новый GET с **актуальными** фильтрами (а не с фильтрами момента начала сохранения).

## Контрольные вопросы

1. **Зачем для загрузки данных нужен эффект, а не запрос в теле компонента?** Тело компонента вызывается при каждом рендере и должно быть чистым; запрос — побочное действие, которое нужно синхронизировать с изменением зависимостей и отменять в cleanup.
2. **Когда React вызывает cleanup?** Перед повторным запуском эффекта при изменении зависимостей и при размонтировании компонента.
3. **Почему callback эффекта не объявляется `async`?** Такая функция возвращает Promise, а React ожидает от эффекта либо `undefined`, либо функцию очистки.
4. **Какие зависимости нужны загрузке и почему в них нет `snapshot`?** `api`, значения фильтров и `revision`. Результат загрузки записывается в `snapshot`, поэтому зависимость от него привела бы к бесконечному циклу.
5. **Почему стабильная ссылка на api важна?** Если `api` создаётся в компоненте заново при каждом рендере, эффект будет перезапускаться бесконечно.
6. **Зачем кроме AbortController проверять актуальность ответа?** Ответ может завершиться, не отреагировав на сигнал отмены (например, подставной API в тестах); признак `active` гарантирует, что устаревший результат не попадёт в состояние.
7. **Почему защита от устаревшего результата нужна и в catch?** Запоздавшая ошибка старого запроса иначе переведёт приложение в `error` поверх свежих данных.
8. **Что проверяет дополнительный цикл StrictMode?** Что setup и cleanup эффекта корректно работают при повторном вызове: пробная загрузка отменяется, актуальный эффект принимает результат.
9. **Почему одной переменной pending в state недостаточно для двух синхронных вызовов?** Обновление состояния применяется асинхронно: второй вызов в том же тике увидит старое значение. Поэтому используется `ref`, меняющийся синхронно.
10. **Что означает true, возвращённое saveTask, если повторный GET завершился ошибкой?** Запись на сервере подтверждена, а ошибка касается только обновления списка; это не `mutationError`.
11. **Почему нельзя автоматически повторять POST после тайм-аута?** Сервер мог уже выполнить создание; повтор создаст дубликат (POST не идемпотентен).
12. **Почему смена фильтров не должна отменять мутацию?** Это отдельная операция записи: её отмена на клиенте не гарантирует отмены на сервере и оставит неизвестное состояние; фильтр влияет только на чтение.
13. **Что происходит с серверной операцией после отмены клиентского ожидания?** Клиент перестаёт ждать ответ, но сервер мог уже выполнить операцию; результат поэтому нужно проверять повторной загрузкой.
14. **Чем meta.total отличается от общего числа записей на сервере?** `meta.total` — число задач после серверных фильтров, то есть размер выборки.
15. **Какие сценарии не проверяются jsdom и требуют браузера?** CORS и предварительные запросы, реальная сеть и throttling, внешний вид и фокус, поведение с настоящей формой и клавиатурой.
