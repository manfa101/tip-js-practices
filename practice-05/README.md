## Эксперимент с очередями выполнения

Команда: `npm run example:order`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Синхронный код идёт первым (A, B, C), затем микрозадачи Promise (D, E), последним таймер (F) |
| Фактический результат | A, B, C, D, E, F | Прогноз совпал |

- К синхронному коду относятся A, B (тело `async`-функции до `await` выполняется синхронно) и C.
- В очередь микрозадач попадают D (обработчик `then` уже выполненного Promise) и E (продолжение после `await`). Они выполняются после завершения синхронного кода и до задач таймера, в порядке постановки в очередь: D раньше E.
- Таймер с задержкой `0` не выполняется немедленно: колбэк ставится в очередь задач таймеров и запускается только после синхронного кода и всех микрозадач.
- Собственный обработчик: после вызова `demonstrateAwait()` добавлен `Promise.resolve().then(...)` с меткой G. Прогноз: A, B, C, D, E, G, F (G ставится в очередь после D и E). Фактически: A, B, C, D, E, G, F. Если убрать обработчик D, исчезнет только его строка, порядок остальных меток не изменится.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API (маршруты задач, категорий, отладочные маршруты); не изменялся |
| `src/api-client.js` | Общий HTTP-клиент: `ApiError`, `buildUrl`, `createApiClient`, `requestJson`. Знает про URL, `fetch`, JSON, тайм-аут, отмену и классификацию ошибок; не знает про задачи |
| `src/task-api.js` | Предметный API: маршруты `/tasks` и `/categories`, проверка фильтров и схемы данных, `loadInitialData` |
| `src/variant.js` | Данные варианта: `variantNumber = 7`, `variantFilters = { q: "провер" }` |
| `src/main.js` | Консольный контрольный сценарий: загрузка, вывод таблицы и отдельно обработанная ошибка `404` |

`fetchFn` передаётся в `createApiClient`, чтобы клиент можно было проверить без реальной сети подменой функции. HTTP-ошибки проверяются отдельно от сетевых: `fetch` не отклоняет Promise при статусе 4xx/5xx, а при сетевом сбое Promise отклоняется, и это разные причины с разным `kind`. JSON после разбора всё равно проверяется по контракту, потому что синтаксически корректный JSON не гарантирует нужную схему (поля, типы, уникальность `id`, `meta.total`).

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `parseBaseUrl`: абсолютный `http`/`https`, без query и hash; слеши в конце и в начале пути не удваиваются | Модульные 01, 04 |
| Кодирование query-параметров | `URLSearchParams`; `undefined`, `null`, `""` пропускаются, `false` и `0` сохраняются | Модульные 02, 03; собственная проверка 1 |
| Заголовок `Accept` | `Accept: application/json` в каждом запросе | Модульная 05 |

| Проверка `Content-Type` | Успешный ответ должен иметь JSON-тип, иначе `invalid-response`; `204` возвращает `null` | Модульные 07, 10; интеграционная 11 |
| Разбор JSON | Тело читается как текст и разбирается `JSON.parse`; `SyntaxError` сохраняется в `cause` | Модульная 11; интеграционная 10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` | Модульная 14; интеграционная 12 |
| Внешняя отмена | Внешний сигнал объединяется с тайм-аутом через `AbortSignal.any`; отказ классифицируется как `aborted` или `timeout` | Модульная 15; интеграционная 13 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]`, `meta.total = 3` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | 1 «Учёба», 2 «Проект», 3 «Организация» |
| `loadInitialData({ completed: false, priority: "high" })` | Объект `{ tasks, categories, meta }`: 3 задачи, 3 категории, `meta.total = 3` |

Правила проверки: задача — положительный безопасный целый `id`, `title` после `trim` от 1 до 100, `completed` boolean, `priority` из `low`/`medium`/`high`, положительный целый `categoryId`; категория — положительный `id` и непустое `name` до 100; `id` в коллекции уникальны; `meta.total` равен длине `data`; `data` — массив. Нарушение даёт `ApiError` вида `invalid-response`. Фильтры проверяются до запроса: допустимы только `completed`, `priority`, `categoryId`, `q`.

## Последовательная и параллельная загрузка

Два запроса `/debug/delay?ms=150`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 363 | 327 | 313 | Время складывается: около двух задержек по 150 мс |
| `Promise.all` | 173 | 169 | 159 | Время близко к одной задержке: оба запроса идут одновременно |

Причина: при последовательных `await` второй запрос начинается только после ответа на первый, а `Promise.all` получает уже начатые независимые запросы и ждёт самый медленный. Измерения получены на этом компьютере и зависят от условий; искусственные задержки в итоговую реализацию не включены.

## Отладка

Точки останова: перед `fetchFn(...)` в `requestJson`, после получения `Response`, перед чтением тела (`response.text()`) и в `catch` при классификации отказа. Значения (получены при запуске тех же запросов):

- **Успешный запрос**: URL `http://127.0.0.1:5505/api/tasks?completed=false&priority=high`; `response.status` — 200; `response.ok` — `true`; `Content-Type` — `application/json; charset=utf-8`; разобранный payload — `{ data: [задачи 4, 13, 34], meta: { total: 3, filters: {...} } }`.
- **Ошибочный запрос** (задача 999): URL `http://127.0.0.1:5505/api/tasks/999`; `response.status` — 404; `response.ok` — `false`; `Content-Type` — `application/json; charset=utf-8`; payload `{ error: { code: "TASK_NOT_FOUND", message: "Задача с id 999 не найдена.", details: { id: 999 } } }`; итоговый `ApiError`: `kind: "http"`, `status: 404`, `code: "TASK_NOT_FOUND"`, `details: { id: 999 }`.
