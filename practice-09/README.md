## Цель и результат

Цель — освоить создание собственного HTTP API на Express: маршруты чтения, разбор query-параметров и идентификаторов, единый формат ошибок, разделение ответственности по модулям. Реализованы `GET /api/health`, `GET /api/categories`, `GET /api/tasks` (фильтры `completed`, `priority`, `categoryId`, `q`), `GET /api/tasks/:id`, ответы `HEAD` и `OPTIONS`, ошибки `400`, `404`, `405`, `500` в формате `{ error: { code, message, details } }`. Данные хранятся в памяти процесса, изменяющие методы возвращают `405`.

## Установка и запуск

Команды выполняются из папки `practice-09`:

```bash
npm ci
npm start
```

API: http://127.0.0.1:5505/api. Проверка окружения: `/api/health`.

Другой порт: `npm start -- 5515`. Режим разработки: `npm run dev`.

Если используется `.env`, запуск: `node --env-file=.env src/server.js`; обычный `npm start` файл не читает. В работе использовался порт 5505 по умолчанию, `.env` не создавался.

## Реализация

| Модуль | Ответственность |
|---|---|
| `src/validation.js` | `parsePositiveId` и `parseFilters`: разбор и проверка id и query-параметров списка, выбрасывает `ApiError` |
| `src/task-service.js` | Чистые функции `selectTasks` (фильтры через И) и `findTask` (поиск по полю `id`) |
| `src/store.js` | Для каждого приложения собственные копии исходных данных; методы `listTasks`, `getTask`, `listCategories` |
| `src/routes.js` | HTTP-обработчики и ответ 405 для остальных методов на известных путях |
| `src/app.js` | Фабрика приложения без открытия порта: CORS и общие заголовки, обработка `OPTIONS`, маршруты, 404 для неизвестных путей, обработчик ошибок |
| `src/server.js` | Разбор порта и запуск `listen` |
| `src/errors.js` | `ApiError` и обработчик ошибок (предоставлен в заготовке) |

- **Нормализация `false`.** `completed` принимает только строки `true` и `false` и явно преобразуется в boolean. Отсутствие ограничения обозначается `null`, а не ложным значением, поэтому фильтр применяется как `filters.completed !== null && task.completed !== filters.completed`: проверка `if (filters.completed)` пропустила бы `false`.
- **Дубликаты и неизвестные параметры.** Для каждого уникального имени из `searchParams.keys()` проверяется принадлежность допустимому набору и `searchParams.getAll(name).length <= 1`; повторения отклоняются даже с одинаковыми значениями. Пустые значения `completed=`, `priority=`, `categoryId=` неверны, а `q=` допустимо.
- **Идентификаторы.** `parsePositiveId` принимает только строки, целиком соответствующие `/^[1-9]\d*$/`, затем проверяет `Number.isSafeInteger`. `parseInt` не используется: он принял бы `4abc` как 4. Результат — число или `null`.
- **Порядок middleware.** Сначала общие заголовки и `OPTIONS` (до маршрутов, в том числе для неизвестных путей), затем маршруты `/api`, затем обработчик 404 для неизвестных путей и в конце обработчик ошибок с четырьмя параметрами. В маршрутах `router.all` для 405 стоит после GET-маршрутов, поэтому `GET` и `HEAD` до него не доходят.
- `meta.total` — размер полученной выборки, а не всего хранилища.

## Контракт

| Метод и путь | Статус | Тело |
|---|---:|---|
| `GET /api/health` | 200 | `{ data: { status: "ok" } }` |
| `GET /api/categories` | 200 | `{ data: category[], meta: { total } }` |
| `GET /api/tasks` | 200 | `{ data: task[], meta: { total, filters } }` |
| `GET /api/tasks/:id` | 200 | `{ data: task }` |
| `HEAD` тех же путей | как у GET | без тела |
| `OPTIONS` любого пути | 204 | без тела, CORS-заголовки |
| другие методы на известных путях | 405 | `METHOD_NOT_ALLOWED`, `Allow: GET, HEAD, OPTIONS` |

```json

```

```text

404: {"error":{"code":"TASK_NOT_FOUND","message":"Задача не найдена.","details":{"id":2}}}                      (GET /api/tasks/2)
405: {"error":{"code":"METHOD_NOT_ALLOWED","message":"Метод POST не поддерживается для этого пути."}}          (POST /api/tasks, заголовок Allow: GET, HEAD, OPTIONS)
```

`meta.total` равен длине полученной выборки (без фильтров — 12). Пустая выборка — это корректный ответ `200` с `data: []`, а отсутствие ресурса — `404`. ## Исправленный дефект

В ходе реализации тесты дефектов не выявили: все 90 проверок прошли с первого запуска. Чтобы показать, зачем нужна проверка всей строки id, выполнен контрольный эксперимент: `parsePositiveId` временно заменён на `parseInt(raw, 10)`.

- **Симптом:** падают 10 модульных проверок (`id отклоняет "0"`, `"-1"`, `"01"`, `"1.5"`, `"1e2"`, `"4abc"`, `" 4 "`, `categoryId=0`, `categoryId=01`, `categoryId=2abc`) и 8 HTTP-проверок (`Некорректный id 0/01/-1/4abc/1.5/1e2`, `categoryId=01`, `categoryId=2abc`).
- **Причина:** `parseInt` разбирает начало строки (`4abc` → 4, `1.5` → 1, `1e2` → 1) и принимает `0`, поэтому недопустимые значения проходят как корректные id.
- **Исправление:** возвращена прежняя реализация: строка целиком проверяется регулярным выражением `/^[1-9]\d*$/`, затем `Number.isSafeInteger`.
- **Повторная проверка:** файл восстановлен и совпадает с исходным (контрольная сумма), `npm test`: 90 из 90 успешно.

## Контрольные вопросы

1. **Чем JavaScript в Node.js отличается от JavaScript в браузере?** Это тот же язык, но разные окружения: в Node.js есть файловая система, сеть, процессы и серверные модули, но нет DOM и `window`; в браузере наоборот.
2. **Что определяет выбор маршрута: путь, query или HTTP-метод?** Путь и HTTP-метод. Query-параметры не выбирают маршрут, а уточняют запрос внутри обработчика.
3. **Чем `req.params` отличается от query-параметров?** `req.params` берутся из частей пути (`/tasks/:id`) и идентифицируют ресурс, query (`?completed=false`) задают условия выборки.
4. **Почему строка `'false'` требует явного преобразования?** Любая непустая строка в логическом контексте истинна, поэтому `'false'` нужно сравнить со строками `true` и `false` и получить boolean.
5. **Зачем проверять весь id и `Number.isSafeInteger`?** Чтобы не принять `4abc`, `1.5`, `01` или слишком большое число, которое теряет точность.
6. **Почему пустая выборка имеет статус 200, а отсутствующая задача — 404?** Список — существующий ресурс, у которого нет подходящих элементов; конкретная задача по id — отдельный ресурс, которого нет.
7. **В чём различие `TASK_NOT_FOUND` и `ROUTE_NOT_FOUND`?** Первый означает, что маршрут найден, но запись с таким id отсутствует; второй — что такого пути вообще нет.
8. **Чем 405 отличается от 404 и зачем нужен Allow?** 405 — путь существует, но метод не поддерживается; заголовок `Allow` сообщает клиенту, какие методы разрешены.
9. **Что означает `meta.total` при активных фильтрах?** Число задач в полученной выборке после фильтров, а не размер всего хранилища.
10. **Как порядок middleware влияет на результат?** Express вызывает их по порядку: `OPTIONS` и заголовки должны быть раньше маршрутов, 404 — после маршрутов, обработчик ошибок — последним; неверный порядок даёт неверные статусы или ответы в HTML.
11. **Почему обработчик ошибок имеет четыре параметра?** По числу параметров (`error, req, res, next`) Express отличает обработчик ошибок от обычного middleware.
12. **Зачем фабрика приложения отделена от открытия порта?** Чтобы тесты создавали экземпляры приложения на свободном порту и с подменой хранилища, а импорт `app.js` не запускал сервер.
13. **Какие данные допустимо отправлять клиенту при внутренней ошибке?** Только общий код `INTERNAL_ERROR` и нейтральное сообщение; стек и внутренний текст исключения не отправляются.
14. **Почему CORS не является авторизацией?** CORS лишь указывает браузеру, каким страницам разрешено читать ответ; другие клиенты (`curl`, серверы) запросы всё равно отправят, поэтому доступ он не защищает.
15. **Какие изменения потребуются в ПР10 для подключения всех действий клиента ПР8?** Методы `POST`, `PATCH`, `DELETE` и `debug/reset`, разбор JSON-тела и его проверка, проверка существования категории при записи, расширение списка разрешённых методов, CORS для `Content-Type` и изменяющих методов.
