## Цель и результат

Реализованы операции записи собственного Express API: создание (`POST /api/tasks`), частичное обновление (`PATCH /api/tasks/:id`) и удаление (`DELETE /api/tasks/:id`) с валидацией тела, серверным назначением id, ответами `201` + `Location`, `200` и `204` и единым форматом ошибок. Выполненный клиент ПР8 подключён к этому серверу без изменений исходного кода: заработали создание, редактирование, смена статуса, удаление и учебный сброс. Данные хранятся только в памяти процесса.

## Реализация

| Модуль | Ответственность |
|---|---|
| `src/task-validation.js` | `validateTaskInput(value, { partial, categoryIds })`: проверка тела POST/PATCH, нормализация (`trim`), все ошибки по полям собираются в `details` одного ответа |
| `src/store.js` | `createTask`, `updateTask`, `deleteTask`: работа с массивом в памяти, серверные `id` и `completed: false`, возврат копий |
| `src/write-routes.js` | Обработчики POST/PATCH/DELETE и ответы по контракту |
| `src/json-body.js` | Проверка `Content-Type`, разбор JSON, ограничение 16 КиБ, пустое тело (предоставлен) |
| `src/errors.js` | `ApiError` и единый обработчик, преобразующий ошибки парсера в `INVALID_JSON`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE` (предоставлен) |
| `src/task-resource.js` | `requireTask`: проверка id и наличия задачи раньше разбора тела (предоставлен) |

- **Назначение id.** Счётчик `nextId` только растёт: берётся текущее значение и увеличивается на 1 при создании. Длина массива не используется, после удаления счётчик не уменьшается, поэтому удалённый id не повторяется.
- **Сохранение непереданных полей.** `updateTask` копирует найденную запись, затем перезаписывает только переданные разрешённые поля (`title`, `priority`, `categoryId`, `completed`) и сохраняет исходный `id`. Валидатор не добавляет значений по умолчанию, поэтому `{ "completed": false }` меняет только статус.
- **Исключение частичных изменений.** Тело проверяется целиком до обращения к хранилищу: при любой ошибке `updateTask` не вызывается, и ни одно поле не применяется (проверено запросом PATCH с корректным названием и категорией 999: ответ 400, запись не изменилась).
- **Типы JSON.** В теле `categoryId` `"2"` отклоняется (в query ПР9 значения были строками, в JSON должны быть числами), `completed` — только boolean (включая `false`). Валидатор собирает новый объект из разрешённых полей, а не применяет spread к `req.body`; неизвестные имена (включая `__proto__`) попадают в `details`, для которого используется объект без прототипа.
- Повторная проверка результата `store.updateTask` в PATCH: `null` (запись удалена, пока читалось тело) даёт 404, а не `200 { data: null }`.

## Контракт

POST `201 Created`, заголовок `Location: /api/tasks/35`:

```json
{"data":{"id":35,"title":"Проверить сервер","priority":"high","categoryId":2,"completed":false}}
```

PATCH `200 OK` для `{"completed":true}`:

```json
{"data":{"id":35,"title":"Проверить сервер","priority":"high","categoryId":2,"completed":true}}
```

DELETE `204 No Content` без тела; повторное удаление: `404 TASK_NOT_FOUND` с `details: { id: 35 }`.

Ошибки `400` (данные для POST: пробелы в названии и категория 999):

```json
{"error":{"code":"VALIDATION_ERROR","message":"Данные не прошли проверку.","details":{"title":"Название должно содержать от 1 до 100 символов.","categoryId":"Неизвестная категория."}}}
```

Различие `INVALID_JSON` и `VALIDATION_ERROR`: `INVALID_JSON` (400) — тело не является корректным JSON или пустое (`{broken`), запрос не дошёл до проверки полей; `VALIDATION_ERROR` (400) — JSON корректен, но поля или их типы не соответствуют контракту.

## Интеграция клиента

- Адрес собственного API: `http://127.0.0.1:5505/api` (порт по умолчанию клиента ПР8). Запросы подтверждены журналом Network: `POST /api/tasks` → 201, `OPTIONS` и `PATCH /api/tasks/:id` → 204 и 200, `DELETE /api/tasks/:id` → 204, после каждой записи повторный `GET` с текущими фильтрами.
- Изменённые файлы ПР8: **изменения исходного кода не потребовались**.
- **Ошибка записи.** При остановленном сервере сохранение формы показывает «Изменение не подтверждено: Сеть недоступна.…», черновик остаётся в поле, блокировка снимается. При `PATCH` для записи, удалённой в другом месте, сервер отвечает 404 `TASK_NOT_FOUND`, ошибка показывается, черновик сохраняется, форма остаётся в режиме редактирования.
- **Ошибка повторного GET** отделена от записи в хуке `useTaskData`: успешная запись остаётся успешной, а ошибка выводится как ошибка обновления списка; автоматического повторного POST нет (подтверждено тестом хука ПР8 № 12). Сценарий блокировки только `GET /api/categories` в DevTools отдельно не воспроизводился.

## Исправленный дефект

В ходе реализации тесты дефектов не выявили: все 174 проверки прошли с первого запуска (после реализации удалён только неиспользуемый импорт `notImplemented` в `store.js`). Чтобы показать, почему PATCH — частичное обновление, выполнен контрольный эксперимент: в `store.updateTask` временно заменено `const next = { ...tasks[index] };` на `const next = {};` (запись заменяется только переданными полями).

- **Симптом:** падают 3 проверки записи: «PATCH сохраняет completed:true при редактировании формы», «PATCH completed:false не сбрасывает поля; фильтр отражает изменение», «PATCH сохраняет непереданные поля и возвращает копию» (77 проверок записи: 74 успешных, 3 неуспешных).
- **Причина:** обновление выполнялось как полная замена записи, поэтому непереданные поля (`title`, `priority`, `categoryId`, `completed`) терялись.
- **Исправление:** возвращена копия найденной записи с последующим применением только переданных полей; `id` сохраняется.
- **Повторная проверка:** файл восстановлен и совпадает с исходным (контрольная сумма), `npm test`: 174 из 174 успешно.

## Контрольные вопросы

1. **Почему проверка формы не заменяет серверную валидацию?** Клиентский код можно обойти (прямой запрос, `curl`, другой клиент), поэтому сервер обязан проверять всё независимо.
2. **Чем частичное обновление отличается от замены записи?** При `PATCH` меняются только переданные поля, остальные сохраняются; замена записи теряет непереданные поля.
3. **Как отличить отсутствующий completed от переданного false?** Через `Object.hasOwn(value, 'completed')` и проверку типа `boolean`, а не по истинности значения.
4. **Почему строковый categoryId в query допустим, а в JSON-теле — нет?** Значения query — всегда строки, их приходится преобразовывать. JSON поддерживает числа, поэтому тип в теле — часть контракта, и `"2"` отклоняется.
5. **Когда следует увеличивать nextId и почему нельзя брать длину массива?** При каждом создании; после удаления длина уменьшается и привела бы к повторному использованию id.
6. **Что произойдёт с данными после перезагрузки браузера и после перезапуска API?** После перезагрузки браузера данные остаются (они в памяти сервера), после перезапуска API возвращается исходный набор.
7. **Зачем POST возвращает 201 и Location?** 201 сообщает, что ресурс создан, а `Location` указывает его адрес (`/api/tasks/35`).
8. **Почему DELETE 204 не должен содержать JSON?** 204 означает «успех без тела»; клиент не должен разбирать JSON такого ответа.
9. **Чем INVALID_JSON отличается от VALIDATION_ERROR?** `INVALID_JSON` — тело не разобралось как JSON, `VALIDATION_ERROR` — JSON корректен, но поля или типы неверны.
10. **Как исключить частичное изменение при ошибке одного поля?** Сначала полностью проверить тело и только после успешной проверки вызывать хранилище.
11. **Почему нельзя бесконтрольно применять spread к req.body?** Так можно записать неразрешённые поля (`id`, чужие свойства, `__proto__`); сначала нужен allowlist полей.
12. **Почему CORS не является авторизацией?** CORS лишь указывает браузеру, каким страницам разрешено читать ответ; прямые запросы он не ограничивает.
13. **Зачем повторно проверять результат updateTask после разбора тела?** Запись могла быть удалена, пока читалось тело; `null` нужно превратить в 404, а не вернуть `200 { data: null }`.
14. **Почему успешный POST и неуспешный GET нельзя считать одной неудачной операцией?** Запись уже выполнена на сервере; повтор POST создал бы дубликат. Нужно показать ошибку обновления списка, но сохранить факт записи.
15. **Что именно проверяют тесты интеграции и что необходимо проверить в браузере?** Тесты — реальный HTTP, адаптеры клиента и контракт сервера. В браузере — работу формы, отображение ошибок, CORS, фокус и внешний вид.

## Вывод

Реализованы операции записи собственного сервера: создание, частичное обновление и удаление с валидацией тела, серверным назначением id и ответами 201, 200 и 204. Тело проверяется целиком до изменения данных, PATCH меняет только переданные поля, счётчик id не уменьшается. Клиент из ПР8 работает с сервером без изменений кода. Данные хранятся в памяти процесса, поэтому после перезапуска сервера возвращается исходный набор. Все 174 проверки проходят.
